Converter documentation

How each converter maps its source format onto a graph

This page documents every source-format converter currently registered in this repository: what it turns each node/edge into, and a full legend for the colors, shapes and edge styles you'll see when you render it in the Demo. It updates itself as new formats and variants are added — see CONTRIBUTING.md for how to add one.

Formats, variants, and the registry

Every converter in this repository extends one shared GraphConverter base class and produces the same { nodes, edges } shape Pivotick expects. Two ideas structure how converters are organized:

  • Format — the source data's identity, e.g. misp. Shared by every converter that can read that kind of input, no matter how it maps it.
  • Variant — one mapping strategy for that format. A source format can have more than one: different ways to turn the same data into a graph topology (which entities become nodes, which relationships become edges). A converter's variant is a distinct choice about graph shape — a pure styling toggle (like Full labels/Debug edge radius, see below) is not a variant.

Every registered format/variant is listed below — this section is generated directly from the ConverterRegistry, the same lookup the Demo's format/variant pickers use, so it can never drift out of sync with what's actually available.

MISP

Variant: Event as root node (event-root)

Each MISP Event becomes one root/cluster node, with everything it carries hanging off of it as children. A standalone Object given with no Event to attach to becomes its own root instead — the converter accepts a single Event, a list of Events, a { response: [...] } restSearch-style wrapper, a standalone Object, or a list of Objects, any mix of these at once, all landing in the same graph side by side.

Concretely, here's what becomes what:

  • Event → root node. Its Attributes and Objects become its children.
  • Object → child node of its Event (or its own root, if standalone), with its own nested Attributes as further children.
  • Attribute → leaf node, child of whichever Event or Object it belongs to.
  • Tag → shared node, deduplicated by name: a tag applied to five different Attributes is one node with five incoming edges, not five copies of the same tag.
  • Galaxy Cluster → shared node, deduplicated by cluster id, same reasoning as Tags. MISP also represents a cluster's association as a plain machine tag (misp-galaxy:type="value") — this converter recognizes that pattern and still treats it as a Tag node structurally, only swapping in the galaxy's own icon and color so it reads as "a tag, but a galaxy one".
  • Object Reference → extra labeled edge between whichever two nodes it names, on top of the structural containment edges above. This is MISP's own explicit, named relationship between Objects/Attributes (e.g. "uses", "dropped-by") — the edge's label is that real relationship type.
  • Galaxy Cluster Relation → extra labeled edge between two Galaxy Cluster nodes, e.g. a threat-actor cluster "uses" a malware cluster. Resolved by cluster UUID; skipped if the referenced cluster wasn't part of the same input.
  • Sightings are not rendered as nodes. They're aggregated into a single sightingCount shown on the owning Attribute — individual sighting timestamps aren't graph-worthy entities on their own.

Variant: Event as root node, simplified (event-root-simplified)

Same entities and relationships as event-root above — nothing about what becomes a node or edge changes. The difference is default visibility, scoped to one relationship only: each Object's own Attributes nest as children of that Object, collapsed by default, using Pivotick's own built-in expand/collapse feature — a small "+" control appears on any node with children; clicking it reveals them, "−" collapses them back.

This is deliberately scoped to only Object → Attribute: an Object is where a MISP export's Attribute count actually explodes (a file or domain-ip Object can easily carry dozens of Attributes), whereas an Event's own top-level Attributes/Objects are usually few enough to read directly — so the Event node itself has no "+" control and stays flat/always-expanded, exactly like event-root. Concretely: an Event with 3 Objects, each holding 20 Attributes, still shows the Event and all 3 Objects immediately (4 nodes) — only each Object's 20 Attributes start collapsed behind its own "+", one Object at a time.

Tags and Galaxy Clusters are unaffected either way — they always stay flat, deduplicated nodes connected by an ordinary edge, in both variants, never nested as children. A node can only be nested under one parent in Pivotick's model, but the same tag (e.g. tlp:white) routinely attaches to many different entities — nesting it would force either duplicating it per parent or picking one arbitrary "owner." Pivotick still re-anchors a Tag/Cluster's edge sensibly when its target is currently hidden inside a collapsed Object.

Rendering

The variant above decides graph topology — what's a node, what's an edge. Independently, every node looks the same way: a real, format-accurate icon per specific type (410 icons, vendored from misp-iconify) inside a colored token, plus the node's name and a small kind chip underneath (see the legend below).

Two toggles refine that default rendering: Full labels lets every badge size itself to its full text instead of clipping long names — at the cost of the fixed-size boxes that keep the edge-connection point predictable. Debug edge radius is a diagnostic overlay (a dashed circle) showing exactly where Pivotick currently anchors each node's edges — not meant to stay on, just useful while checking a custom-rendered badge isn't visibly overlapping its neighbors.

Node kind legend

Every node classifies into one of these 13 broad kinds, shown as the small chip under its icon badge — alongside the badge's own icon/color, which comes from a finer 6-category split (event / tag / attribute / object / galaxy cluster / generic) plus the specific misp-iconify icon layered on top.

Edge legend

One rule decides whether an edge gets an arrowhead: edges that represent plain containment ("this belongs to that" — an Event holding an Object, a Tag applied to something) never carry one, since they're not a directed relationship. Edges that represent a real, named relationship an analyst cares about — an Object Reference, a Galaxy Cluster Relation — keep theirs, and are usually labeled with the actual relationship name from the source data.
